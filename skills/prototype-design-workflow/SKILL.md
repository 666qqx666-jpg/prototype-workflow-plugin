# 原型设计工作流

## 核心定位

本 skill 是通用「原型设计」入口，不等于高保真生成器。

它负责先判断当前任务属于哪种原型模式，再决定应该先补什么前置产物、能不能进入高保真，以及最终使用线框图、单文件 HTML、React 还是目标项目当前技术栈。

PRD 完成后不一定进入原型。只有当用户当前意图已经指向页面、交互、状态呈现、线框、高保真、既有系统增量或原型审查时，才使用本 skill。

## 触发边界

使用本 skill 的场景：

- 把 PRD、需求文档、brief、spec 或产品想法转成页面结构。
- 设计低保真线框、用户路径、页面地图或交互流程。
- 创建单文件 HTML 高保真原型。
- 基于原平台、原代码、截图、旧 HTML、现有后台页面做增量原型。
- 审查一个原型是否符合 PRD、原平台基线或用户标注。
- 讨论筛选、表头、列表、卡片、抽屉、弹窗、入口、状态、空态、异常态如何呈现。
- 用户说“看页面怎么落”“画一下交互”“做个原型看看”“在原页面基础上改”。

不要使用本 skill 的场景：

- 用户只是要写 PRD，应走 PRD 写作流程。
- 用户只是要审查 PRD，应走 PRD 审查流程。
- 用户明确说进入 spec、写实施计划、创建 plan、开始开发，应走对应 spec / writing-plans / implementation 流程。
- 用户只是要纯技术实现，不讨论页面或交互呈现。
- 用户明确跳过原型，不要插入原型必要性判断。

## 总流程

1. 先判断是否可以走快速通道。
2. 如果不能走快速通道，再选择三种主模式之一：
   - 既有系统增量
   - 0→1 新项目
   - 半参考型
3. 对材料做角色分层：项目本体、入口承载页、页面基线、组件参考、业务能力参考、历史背景、反例。
4. 根据模式补齐前置产物。
5. 通过原型门禁后，再选择产出形态。
6. 如果要派生 Codex fork 诊断子分支，不在主分支预置大段上下文包；提示 fork 后先让子分支自生成边界卡。只有非 fork 分工且没有继承上下文时，才生成简版任务卡。
7. 交付后按 PRD、原平台基线或前置产物做验收说明。
8. 进入既有系统高保真前，独立判定 `baseline-evidence`；真实页面证据不足或冲突未裁决时，不得用旧原型或常见后台经验补位。
9. 原型收敛后，独立判定 `prototype-sync`；产品口径已经变化但尚未同步时，不得宣布原型完成或封口。

## 快速通道

当已有 PRD、spec、plan、原型方案、线框说明、截图标注或用户确认过的页面关系已经足够明确时，走快速通道。

快速通道下不要重新头脑风暴，不要反复问产品方向。读取已有产物，做简短 readiness 判断，然后直接生成原型并验收。

如果用户说明 plan 已确认，但当前消息没有附上内容或路径，只索取该 plan
本身或其路径；仍标记为快速通道，并在取得材料后直接生成，不退回产品讨论。
用户同时明确“不需要开发交付说明”时，在回复中确认采用“快速通道（light）”；
不得创建 change manifest、右卡、编号、连线或开发阅读器。

快速通道 PASS 条件：

- 页面范围明确：要做哪些页面、弹窗、抽屉、状态。
- 交互路径明确：入口、跳转、操作反馈、异常 / 空态。
- 状态呈现明确：默认态、筛选态、已处理 / 未处理、权限态等。
- 视觉约束明确：有原平台基线就按基线；无基线就按已确认风格。
- 产出形式明确，或材料足够让 agent 判断产出形式。

如果这些条件不满足，不要强行走快速通道，进入模式路由。

## 模式一：既有系统增量

适用于：

- 有原平台、原代码、真实截图、旧 HTML、现有后台页面。
- 用户说“在原页面基础上改”“参考现有平台”“按原代码复刻”“旧页面加功能”。
- 原型目标是新增字段、筛选、按钮、状态、抽屉、弹窗、列表列或局部交互。

核心原则：

原平台不是灵感参考，而是验收基线。先理解并复刻相关原平台基线，再讨论新功能插入点。

如果工作区已经存在本项目原型，当前源文件是唯一业务修改基线。先记录路径、Hash、
版本状态和未提交改动，再在该文件上做最小增量；不得另建一个替代页面后把新页面、
右侧阅读器、整合快照或截图称为“当前原型”。派生产物只能用于阅读和验收。

既有系统不等于已有本需求原型。经限定检索及用户确认尚无本需求旧原型时，允许首次生成；先用 `first-baseline-create` 锁定确认记录与唯一输出路径，不创建伪旧 HTML。仍使用既有系统增量模式及完整真实产品基线，不切到 0→1 或标为不适用。执行细则见 `references/local-source-and-first-generation.md`。

如果当前需求属于一个长项目下的子项目，先把项目层级说清楚：这个子项目属于哪个长项目，哪些页面只是入口承载，哪些旧项目不能被当成本体。不要因为某个旧页面被改动，就把复盘或原型归入旧项目。

进入高保真前必须输出：

1. 材料角色表

   把读到的材料分为：
   - 项目本体：本次真正要解决的需求对象。
   - 入口承载页：会被改到或覆盖到，但不是项目本体。
   - 页面基线：结构、列数、模块顺序和交互必须继承的真实页面。
   - 组件参考：只参考局部交互或组件形态。
   - 业务能力参考：只参考对象、接口、状态或规则。
   - 历史背景：解释上下文，但不直接决定本次页面结构。
   - 谨慎参考 / 反例：容易误导，必须标注不能替代基线。

2. 页面关系矩阵
   标明每个页面、弹窗、抽屉、二级视图是：
   - 新建页面
   - 复用原页面
   - 原页面扩展

3. 现有结构保留清单
   至少覆盖：
   - 页面骨架
   - 列数、模块顺序和字段分组
   - 导航与入口
   - 顶部概览
   - 搜索筛选
   - 表头 / 列表 / 卡片形态
   - 操作按钮
   - 详情页 / 抽屉 / 弹窗
   - 状态标签
   - 权限与异常态
   - 视觉密度、间距、字号、圆角、边框、hover

   复用页面首先是结构复用，不是字段抽取后重新排版。用户没有明确要求重设计时，一列详情不能变两列，原模块不能重新卡片化。

4. 本次增量变化清单
   只写本次允许新增、删除或调整的字段、按钮、筛选、状态、统计口径或交互路径。
   对每个新增点写清插入位置：哪个模块、哪个字段前后、是否影响底部操作区。

5. 规则呈现分层表
   对每条会影响页面或操作的规则，先判断它应由页面可见内容、交互行为 / 反馈、原型外部标注，还是 PRD / 接口 / 验收说明承载。不要因为规则重要，就把实现说明直接写进页面。

6. 真实页面基线证据包

   Candidate 代码来源有两个明确分支：中心机来源必须通过版本锁定的 `enterprise-prototype-code-query` launcher；本机来源只接受用户明确授权的特定项目根和精确文件清单，通过 `local-code-capture` 锁定授权证据和全部文件摘要，不改变 SSH 服务配置或安装门。读取 `references/local-source-and-first-generation.md`。不得因远程项目不可见或失败就静默切到本机，不得推定本机目录存在即有授权。中心机新 Run 前先执行服务 `doctor`（仅认证和一次 list，不代表项目授权）。用户未选定项目时只请求唯一目标项目，不执行 overview/search/read；选定项目与范围后才定向查询。项目不可见、查询失败、空结果或错误对象均输出 baseline-evidence: BLOCK / restart_required，不生成成功来源，不取消基础安装；明确授权本机来源后只重启受影响的来源绑定，不跨版本续跑。list PASS、命中列表和错误文本不能代替真实代码；至少精读主页面、核心组件、样式、接口、路由、状态与权限定义，记录项目、关键词和相对路径。私钥路径、SSH 用户名和原始错误不得进入 `current-code`。Snapshot 后只验证已锁定本地来源，不重查或替换证据。本机 Git HEAD 不能自动证明线上部署版本，代码与真实页面的版本关系或关键冲突未核实仍阻断。

   证据包至少逐项记录：

   | 证据项 | 要回答的问题 |
   | --- | --- |
   | 项目本体与入口承载页 | 本次项目是什么；哪些页面只是承载同一能力的入口 |
   | 当前宿主页面 | 真实入口、路由、页面骨架、导航和操作区是什么 |
   | 核心组件 | 列表、卡片、抽屉、弹窗、筛选器分别复用哪个现有组件 |
   | 样式与设计体系 | 当前组件库、字号、间距、边框、状态色和密度从哪里确认 |
   | 状态与数据呈现 | 哪些状态、字段、权限、空态和异常态会改变页面呈现 |
   | 证据来源 | 当前代码、真实页面 / 截图、用户确认、现行文档、旧 HTML 分别支持什么结论 |
   | 缺失或冲突 | 哪些关键结构尚未核实；不同来源之间是否互相矛盾 |

   证据优先级按“用途”区分，不能混成一个总排序：

   - 产品目标与最终交互口径：当前最终 PRD、已确认决策和用户本轮裁决优先。
   - 现状页面结构与视觉基线：当前真实页面、现行代码和同版本截图优先。
   - 旧 HTML、旧原型、历史文档和竞品参考：只用于追溯或局部参考，不能覆盖当前事实。

   如果当前代码、真实页面和截图不一致，先列出差异并确定本轮采用的版本；不能自行选择“看起来更合理”的一个。

   基线采集顺序固定为：实际走查当前可交互页面 → 定向检索当前代码 → 冻结同版本
   截图。代码可得却未检索、只有截图却需要判断动态交互、或三类来源冲突未裁决，
   一律 `baseline-evidence: BLOCK`。代码确实不可用时记录原因；不能用“已参考代码”
   代替检索证据。门禁在 skill 内 fail closed，不再向用户追加一次“是否继续”确认。

验收时，未出现在“本次增量变化清单”里的变化，默认不允许进入高保真原型。

如果用户指定某个参考组件但找不到，先暂停并说明：

- 已查找的页面、关键词、代码路径或截图。
- 为什么没找到或不确定。
- 当前最接近的替代参考。
- 继续前需要用户补充的最小材料。

不要在找不到组件时凭理解继续做成相似但错误的交互。

## 模式二：0→1 新项目

适用于：

- 没有原平台、原代码或真实页面基线。
- 用户从产品想法、需求文档、brief、竞品启发开始，希望先看产品形态。
- 当前目标是把抽象需求变成用户路径、页面地图、信息架构和线框。

进入高保真前默认输出：

1. 原型前需求摘要
2. 用户路径
3. 页面地图
4. 信息架构
5. 关键状态清单
6. 低保真线框
7. 涉及关键操作时的规则呈现分层

原型前需求摘要不是新 PRD，只压缩会影响页面和交互的内容。建议包含：

- 原型目标
- 主要用户与场景
- 核心路径
- 页面范围
- 关键状态或需要收敛的问题
- 本轮不做边界

如果 PRD 已经非常清晰，摘要控制在 5 行以内，不单独成表。

## 模式三：半参考型

适用于：

- 用户提供竞品、截图、旧项目、设计风格或示例页面。
- 这些参考不是当前系统真实基线。
- 用户既想借鉴，又不希望照搬或误继承。

进入高保真前输出：

1. 参考来源清单
2. 硬继承 / 软参考 / 禁止照搬边界
3. 本项目页面地图
4. 低保真线框

要明确区分：

- 硬继承：必须保持的结构、路径、组件或视觉约束。
- 软参考：只借鉴思路、节奏、信息组织或交互方式。
- 禁止照搬：品牌、文案、业务逻辑、专属布局或不适合本项目的部分。

## 原型门禁

不许直接高保真，但允许低保真探索。

低保真探索的目的不是交付最终设计，而是暴露并收敛 PRD 到页面之间的呈现选择。

门禁规则：

- 业务规则未封口：回 PRD / PRD 审查，或标记为需求缺口。
- 页面关系未封口：先做页面关系矩阵，不进入高保真。
- 状态呈现未封口：允许做低保真 A/B 线框，帮助用户收敛。
- 原平台基线未冻结：先做基线复刻清单，不进入高保真。
- 小字段、小顺序、小文案未定：可以继续低保真探索，但必须标注假设。
- 高保真只在业务规则、页面关系、状态呈现、基线约束都足够明确后开始。

### 真实页面前置门（既有系统增量强制）

既有系统增量在开始高保真前，必须给出两个独立判定：

```text
baseline-evidence: PASS / BLOCK / NOT_APPLICABLE
high-fidelity-readiness: PASS / BLOCK
```

- `baseline-evidence: PASS`：目标宿主页面、核心组件、结构与视觉约束、状态 / 权限呈现均有可验证来源，且关键冲突已裁决。
- `baseline-evidence: BLOCK`：找不到目标页面或指定组件、只有旧 HTML / 历史文档、关键入口或结构证据缺失，或当前代码、截图、真实页面互相冲突且未裁决。
- `baseline-evidence: NOT_APPLICABLE`：真正的 0→1 项目或用户明确授权完全重设计；必须写明理由，不能因为证据难找就标不适用。
- `high-fidelity-readiness: PASS`：除证据通过外，页面关系矩阵、现有结构保留清单、本次增量变化清单和规则呈现分层表均已完成。
- 任一关键项为 BLOCK 时，只允许补证据或做明确标注假设的低保真探索，不得进入高保真实现。

旧原型“看起来完整”、代码查询“命中过文件”或 agent 写了“已参考原平台”，都不能单独使前置门通过。

## 规则呈现载体门禁

原型要让规则可追溯，但不等于把规则解释写进页面。页面只承担用户当前需要理解、选择或规避的内容；实现口径和验收口径要留在正确的载体中。

对每条会影响页面或操作的规则，先归入以下一种或多种载体：

| 承载位置 | 适用内容 | 页面上的正确形态 |
| --- | --- | --- |
| 页面可见内容 | 用户必须据此做当前选择、理解操作结果或规避不可逆风险 | 简洁的对象、结果、范围或风险提示 |
| 交互行为 / 反馈 | 系统需要校验、拦截、确认、保存或刷新，但用户不需要理解内部机制 | 禁用态、字段错误、提交失败原因、保存结果、必要的二次确认 |
| 原型外部标注 | 评审者需要知道，但普通用户不需要在操作时阅读 | 原型标注、交互说明、状态说明 |
| PRD / 接口 / 验收 | 后端数据口径、批量处理方式、记录生成、字段映射、幂等、校验规则和测试条件 | 不进入页面文案；在文档或验收项中可追溯 |

页面可见性判断按以下顺序执行：

1. 这条信息是否会直接改变用户当前的选择、操作结果或风险判断？不是，则不放页面。
2. 用户是否必须理解它才能避免误操作、不可逆覆盖或结果意外？是，则页面只给出与动作直接相关的简洁提示或确认。
3. 这条话是否在解释系统如何处理数据、调用接口、生成记录、执行校验或覆盖范围？是，则默认属于原型标注、PRD、接口或验收，不进入页面。
4. 页面文案中不得出现仅供内部协作理解的对象和术语，例如 MCU、数据写入、标签标注记录、接口、校验链路、全量覆盖逻辑；除非这些本来就是该用户的业务对象且用户确实需要据此操作。

常见转换：

- “保存时以本次操作为准”不是默认页面说明；只有存在不可逆覆盖且用户需要决定是否继续时，才在确认弹窗中写成简洁结果提示，例如“保存后将替换当前已选标签”。
- “提交前校验”不显示为页面规则；校验失败时，在对应字段或提交反馈中说明用户可修正的原因。
- “统一覆盖标注范围内全部 MCU，并按 MCU 分别生成客资标签标注记录”属于数据处理和验收口径，应留在 PRD / 接口 / 验收说明。页面只表达用户可感知的对象、范围和结果，例如“将为已选对象更新标签”。

如果无法判断某条规则是否需要页面可见，先把它列入规则呈现分层表并标为待确认；不要为了“原型完整”把内部说明塞进页面。

## 产出形态选择

默认高保真交付形式：单文件 HTML。

使用低保真线框：

- 页面地图还没定。
- 核心路径还在讨论。
- 状态呈现方式未收敛。
- 既有系统增量还没确认插入点。
- 用户需要先看结构，而不是最终视觉。

使用单文件 HTML：

- 需要快速可看、可交互、低依赖的高保真原型。
- 单页或少量页面 / 状态切换。
- 适合快速评审和多轮修改。
- 不需要接入真实工程。

使用 React：

- 多页面、多状态、复杂交互。
- 需要复用组件。
- 原型后续会持续迭代。
- 单文件 HTML 已经难以维护。

使用目标项目当前技术栈：

- 既有系统的框架、组件库和版本已有当前代码证据。
- 用户明确要求贴近开发实现。
- 需要组件级一致性，且单文件 HTML 无法稳定复刻。
- 多页面、多状态或复杂交互需要持续迭代。

不要把“换框架”当成保真失败的默认解法。HTML 画得不像，优先检查是否已经冻结原平台基线。

对于既有系统，任何产出形态都必须先按当前页面和代码中的真实组件思维复刻：

- 筛选区顺序和密度
- 表头和列顺序
- 表格、卡片列表和分页行为
- 抽屉宽度、分组和 footer
- 按钮、标签、状态色
- 容器、边框、间距、字号层级
- 空态、异常态、hover、禁用态

不得引入目标产品当前未使用的新设计体系，除非用户明确授权重设计。

## 开发可读性交付

当原型需要交付开发、说明本次需求变化，或 PRD 与原型距离较远时，读取
`references/developer-readable-prototype.md`。

0.1.19 新 Standard 必须使用 v4 change manifest 和本地 evidence bundle。从同一份 manifest
生成页面标记和右侧开发说明，但 manifest 不能自证：标题、摘要、变化内容及每个
字段 / 规则 / 交互 / 异常都要绑定可校验 Hash、定位符和摘录的 PRD、用户裁决、
真实页面走查或当前代码。每个目标语义必须至少绑定一条当前 PRD 或已确认产品
裁决；runtime / code 只能补充现状、位置和继承约束，不能单独授权标题、结果、
字段、规则或交互。截图和原型基线不能证明产品语义；来源缺失或仍有歧义时写入
阻断性 pending item，不得用默认值把结构填满。

evidence bundle 必须记录与 manifest 一致的来源类型和原始定位，并由 validator 的
`--evidence-root` 限制到明确材料根目录。v2/v3 仅允许历史只读或显式沿革基线，不可作为新 Standard 成功产物。既有原型增量还要在 manifest 记录当前源
文件相对 `--workspace-root` 的路径、修改前快照与 Hash；validator 必须同时验证
当前文件身份、修改前基线和修改后 Hash，不能只接受 `sourceRole` 自我声明。
workspace root 必须是任务开始时发现的真实工作区；evidence roots 只能来自用户给定
材料、现有项目材料目录或已记录的任务来源。不得为了通过校验，把任意文本复制进
新证据目录、把任意目录声明成 root，或把 Skill / 实现说明改标为 PRD。来源权威
无法由既有材料确认时，直接命中独立复核。

按活动界面容器限制编号、高亮和连线。每张可定位卡必须同时通过：真实且可见的
anchor、右卡到原型、原型到右卡、可见连线、返回后状态恢复。`body` / `#root`
等虚拟容器以及 anchor 等于 surface root 均失败。跨页面通用规则进入
`globalRules`，明确至少适用两个页面、不生成页面编号、锚点或连线；出现按钮、入口、
字段、点击、打开抽屉等位置 / 动作语义时直接失败，能定位的规则不得借此逃避验收。
`scope`、`appliesToPageIds` 和 `nonLocatableReason` 本身也必须绑定含“全局 / 所有页面 /
跨页面”等明确范围表述的权威证据，不能由执行者自行把页面规则归类为全局规则。
每个 surface 的状态快照必须覆盖其 root；返回时不得通过替换 `innerHTML` 伪恢复，
并要在同一个活页面连续执行两轮定位与返回，验证可见结构、控件、容器与页面滚动
均一致，以暴露只在第二次交互出现的 JavaScript 状态泄漏；连线两端必须实际位于视口内。

运行 reference 中的 validator，任何错误均 fail closed。自动语义门只证明“证据
真实存在且已绑定”，不证明对证据的解释必然正确；首次真实使用、规则改变、复杂
跨页面 / 全量交付、证据缺口或冲突、自动降级或同类失败复现时，必须增加独立复核。
命中风险时，复核方必须产出绑定 manifest、原型和 evidence bundle 精确 SHA-256 的
独立 review record；制作方不得自行填写“independent=pass”。校验器可以验证复核对象
和触发项一致，但不能认证组织身份，因此复核记录必须来自任务中的独立复核者。
普通交付使用完整自动门加抽样检查。人类阅读用时只作为可选观察，不阻断发布。

## 与 PRD 审查结果衔接

如果有 PRD 审查结果：

- PASS：可以进入原型模式路由。
- BLOCK：不要直接高保真；可以解释缺口、做低保真探索，或建议回 PRD。
- 交互封口建议：转成页面关系矩阵、状态呈现问题和验收清单。

如果没有 PRD 审查结果：

只做原型 readiness 检查，不重新做完整 PRD 审查。检查范围包括：

- 页面范围
- 用户路径
- 关键状态
- 原平台基线
- 验收约束

原型过程中发现新的业务不确定项，不强制停止原型。先标注为假设或待确认点。

当原型反馈改变以下内容时，提示后续回写 PRD：

- 页面关系
- 筛选口径
- 状态可见性
- 入口
- 抽屉 / 弹窗行为
- 验收项

纯视觉微调、间距调整、小文案优化，不需要每次回写 PRD。

## 原型结束同步门

开发可读性交付使用当前 Standard Manifest v4 和 Independent Review v2。同一需求的后续交付必须继承既有累计阅读稿：保留卡使用稳定 `cardId` 并按最终阅读顺序连续重编号；旧 pending 必须明确续留、由当前权威来源关闭或被新问题替代。产品范围、用于复刻的样本和本轮实测覆盖分开记录。事实来源详情独立收起，卡片展开、定位和返回不改变来源展开状态。

对由受支持的产品冻结清单绑定的历史累计阅读稿，可在全新 Run 调用 `scripts/migrate-frozen-review.mjs` 生成当前可编辑 Manifest、当前 Reader Shell Snapshot 和 lineage baseline receipt。迁移只支持描述符明确列出的历史契约；必须同时提供当前 PRD、该 PRD 的明确版本标签与预期 SHA-256、当前原型、旧 Manifest、唯一旧 Reader、旧构建 metadata 和包含这些产物的冻结目录。`--prd` 可以指向历史权威路径，也可以指向用户明确选定的冻结副本；副本模式必须由版本标签和实际摘要共同绑定，并在描述符中保留旧冻结权威路径、归档路径与摘要关系，不能通过改写旧 Freeze 或覆盖实时 PRD 获得通过。迁移按原始 Hash 保留全部历史文件，并验证可继承 PRD 引用、卡片/页面范围及新 Reader 的八项核心运行能力；未知格式、伪造描述、缺项或摘要不匹配均拒绝。它不会补造旧文件未记录的字段、事实来源或产品裁决。详细字段、历史只读规则、receipt 和可选三件套冻结命令见 `references/developer-readable-prototype.md` 与 Candidate Runbook。

产品三件套冻结必须绑定 Enterprise Standard `validate-output` 生成的实际成功回执：冻结命令同时传入 `--validation-receipt <validation-receipt.json>`，收敛记录的 `localValidation.receiptSha256` 必须等于该文件字节摘要。冻结完成后，继续执行 `builder-handoff --product-freeze-manifest <FREEZE-MANIFEST.json>`；Builder 会将 Freeze 摘要写入 Handoff，并复核 PRD、原型、Reader Snapshot、Manifest 和 Evidence 与当前回执一致。若冻结后产物变化，重新开始本轮 Run。

当用户要求“最终原型、交付、封口、结束、进入 spec / plan / 开发”时，必须判定：

```text
prototype-sync: PASS / BLOCK / NOT_REQUIRED
```

- `PASS`：最终原型、PRD / 决策记录、验收口径和项目入口对本轮所有产品级变化已经一致。
- `BLOCK`：原型中已经形成新的产品裁决，但 PRD、验收或决策记录仍保留旧口径；存在互相冲突的活跃原型、旧弹窗 / 按钮 / 状态残留，或无法判断哪个文件是最终版本。
- `NOT_REQUIRED`：本轮只是低保真探索、视觉试验或局部审查，用户没有要求封口；必须留下未同步清单和下一次触发条件。

结束同步按以下顺序执行：

1. 汇总本轮及之前尚未回写的原型裁决，不只检查最后一次修改。
2. 将变化分为：
   - 产品级：页面关系、入口、筛选口径、状态可见性、操作位置、抽屉 / 弹窗行为、权限、异常反馈、验收结果。
   - 呈现级：间距、颜色、圆角、阴影、密度和不改变语义的小文案。
3. 产品级变化必须进入“原型裁决同步表”，明确同步到 PRD 章节、验收项、决策记录或项目入口；呈现级变化可只留在原型。
4. 原型反馈与当前 PRD 冲突时，拒绝静默覆盖。当前 PRD 仍是产品事实，直到用户裁决并授权回写；未获修改授权时标记 `prototype-sync: BLOCK`，列出待同步项，不擅自改 PRD。
5. 检查正式交付物内是否仍有会误导后续读取的旧交互文案、旧组件、死代码入口或多个“最终版”。能删除则删除；暂不能删除时明确标记废弃和唯一真值源。
6. 只有项目阶段、正式产物或后续加载入口发生变化时，才更新项目总索引、材料索引或后续拆分索引；纯视觉修改不触发项目级索引更新。

最低同步表：

| 原型裁决 / 变化 | 类型 | 当前事实 | 需同步位置 | 状态 |
| --- | --- | --- | --- | --- |
|  | 产品级 / 呈现级 | PRD / 用户裁决 / 原平台基线 | PRD章节 / 验收 / 决策记录 / 原型 / 项目索引 | 已同步 / 待授权 / 冲突 / 不需同步 |

没有产品级变化时，也要明确记录“本轮仅呈现级调整，无需回写 PRD”，不能静默跳过同步判定。

## 宿主适配

核心原型方法不假设当前运行在 Codex、Claude 或 OpenClaw。

- 当前宿主支持 Codex fork、派生任务或诊断分支时，读取 `references/host-codex.md`。
- 不支持 fork 时，保持单对话执行；只有明确的非继承式多 Agent 分工才生成简版任务卡。
- 宿主适配不得改变页面基线、产品事实来源、门禁状态和交付验收。

## 交付验收清单

交付原型时，必须说明：

- 使用了哪种模式。
- 是否走了快速通道。
- 读取了哪些 PRD、spec、plan、截图、代码或参考材料。
- 是否存在原平台基线。
- 已保留哪些原结构。
- 本次只做了哪些增量变化。
- 每条关键规则由什么载体承载；页面是否混入了后端、数据处理或验收说明。
- 产出了哪些页面、状态和交互。
- 还剩哪些假设或待确认点。
- 是否建议回写 PRD。
- `baseline-evidence` 与 `high-fidelity-readiness` 的判定。
- `prototype-sync` 的判定；若不是 PASS，列出未同步项和阻断的下一阶段。
- 原型如何对照 PRD、原平台基线或计划进行验收。
- 如果本轮包含开发可读性交付，确认 manifest、范围、字段 / 规则 / 交互、
  事实来源绑定、活动界面容器、双向定位、可见连线、返回状态和只读构建均通过
  reference 的自动门；同时说明本轮是否命中独立复核触发条件及结果。

既有系统增量额外说明：

- 页面关系矩阵是否被遵守。
- 现有结构保留清单是否被遵守。
- 本次增量变化清单是否被遵守。
- 是否存在未授权的新模块、新字段、新流程或新视觉体系。
- 是否把内部数据术语、记录生成方式、接口 / 校验逻辑或验收描述误写成用户页面文案。
- 是否确实修改了当前工作区原型源文件，而不是用派生页面替代。
- 是否提供了真实页面走查、定向代码检索和同版本截图的证据；若代码不可用，原因是否明确。

0→1 新项目额外说明：

- 用户路径是否闭环。
- 页面地图是否覆盖核心场景。
- 关键状态是否覆盖默认态、空态、异常态、权限态。
- 线框或高保真是否回答了本轮要收敛的问题。

半参考型额外说明：

- 哪些参考被硬继承。
- 哪些参考只是软借鉴。
- 哪些内容明确没有照搬。
- 最终方案如何回到本项目目标，而不是被参考对象牵着走。
