# 既有交互的继承与增量验证

在既有系统首次生成、增量修改或保真审查时读取。使用 SKILL 中已有的材料角色表、保留清单和变化清单，不新增收据、状态门或强制审查轮次。

## 从“读过材料”到“保留操作”

先从宿主页面和截图提取主要区块之间的关系，再进入组件细节。将这些事实写进已有的结构保留清单，每个受影响的复用页至少覆盖其主要模块。列明来源位置、容器、顺序或方向、哪些区块在同一状态同时显示、哪些要经某个入口才出现。例如来源若显示“摘要下方常驻明细”，验收时从原入口进入，直接向下滚动就应看到明细。若来源确为标签切换，则应验证切换前后的可见面板。布局预期取自原材料，批准的变化以当前需求为准。

交付前，在实际 HTML 上进入清单对应的状态。Standard 在最终 Reader 的业务 iframe 中检查。先核对容器、出现方式和相对位置，再执行相关操作并记录结果。两个模块都能找到或两个功能都能使用，仍需要核对它们是否需要额外点击才能看到。对暂缺来源或未实测的关系，逐项标明。

需要可重复检查时，用包内 `scripts/assert-region-order.mjs` 的 `assertRegionOrder(container, {first, second, order})`。container 为当前业务容器的 Playwright Locator，first 和 second 为相对于容器的唯一 CSS 选择器，order 取 `above` 或 `left-of`。在同一状态采样实际渲染位置，允许页面滚动。对切换面板，按来源另测点击前后的显示与隐藏。具体区块名称、排列方向和尺寸取自该项目，记录在任务的验证脚本中。

截图确认形态，代码与实际操作确认行为。对本次触及的复杂组件，将已有保留清单细化到能实际操作的粒度；不要记录一句“沿用选择器”后换成另一种组件。

| 对照项 | 在原材料中确认 | 在生成结果中实际检查 |
| --- | --- | --- |
| 选择组件 | 容器形态、两侧搜索／筛选、单选或多选、移入移出、限制、确认与取消 | 从各真实入口操作，检查未确认选择与已保存结果的区别 |
| 详情表单 | 字段分组和顺序、说明、默认选中、入口差异、重置／取消／保存各自含义 | 用已有值和未完成资料进入，检查重置、关闭、保存后的结果 |
| 列表操作 | 查询触发时机、重置、计数、下载、批量操作、分页与操作位置 | 不能把显式查询擅改为输入即筛，不能因正文未重述就删掉继承按钮 |
| 新建页面 | 本期明确的页面字段和操作、获准复用的局部组件 | 不从对象完整数据结构自动生成创建人、更新时间等额外列 |

上述是检查维度，不是所有产品都必须具备的功能。没有该能力的原系统不新增它。每个实际变化需要当前 PRD 或已确认裁决支持；同一组件在不同入口有不同约束时分别记录，不能统一套一个默认值。

在原有保留表中增加必要的“操作／预期结果／实际结果”即可。验证失败时修正结果，不把“已参考代码”改写成通过。优先覆盖本轮触及且最容易被简化的组件，不无差别遍历全站。

保留清单与变化卡承担不同职责：原有查询、保存、重置和选择器进入保留清单，仍要在生成结果中操作验证，但不因此新增说明卡。复杂选择器至少用一次取消和一次确认检查草稿与已保存值，涉及顺序时检查最终消费顺序；仅证明按钮存在或选中值非空不能证明继承完成。

把每个本轮触及的复杂组件写成一条可执行操作序列：**原始代码位置 → 原入口与容器 → 草稿如何改变 → 取消结果 → 确认结果 → 新原型实际入口与实测结果**。生成前补全原材料一侧，生成后补实测一侧。不要只列功能名。组件来自依赖包时，读取实际子组件或获准复用的原始操作记录；调用方只出现组件名不代表内部行为已查清。

例如，原来是“已选数量→配置→独立弹窗→选择→确定/取消”，直接在表单铺复选框会丢失提交边界；原来是“展开筛选→编辑条件→确认/取消”，常驻下拉且即时生效会改变操作。这些不能以功能等价为由替换。原单选排列不自动改成下拉。业务数据可以虚构，入口、容器、选择过程和提交边界不能用简化演示代替。对被复用页面列出原有行操作，逐项保留或给出明确批准的删除依据。

只检查已恢复的简单操作会漏掉核心偏差。先验证上述最易被简化的完整序列，再验证普通查询/保存；存在未保留组件时，不以其他操作通过数抵消，也不写整体保真PASS。作者可调试自己的草稿，但最终一笔修改后重跑受影响操作；测试结果必须对应交付字节。

## 阅读定位是临时导航

对本次复用的关键控件，保留清单同时写入可定位的原样式声明、尺寸和适用断点。匹配视口下用 `assertRegionSize(locator, {height: 原高度})` 或 width 核对实际边框盒，考虑原 box-sizing。自适应组件按来源检查范围或比例。尺寸从当前组件取得。

Standard使用包内Reader及原校验，不能另写轻量替代稿。编写业务页时就让进入/退出操作可逆：在打开抽屉或弹窗前保存原业务草稿和显示模型，取消/退出时通过同一渲染函数恢复。初始化也调用同一渲染路径，避免首次隐藏弹窗留有静态占位文本，退出后却变成另一套动态文本。

Reader默认恢复控件、类名与滚动。有动态列表、嵌套选择草稿或JavaScript显示模型的业务页，还应提供同步适配器 `window.__PROTOTYPE_READER_STATE__ = {capture, restore}`：`capture()` 返回可JSON序列化的完整临时状态；`restore(saved)` 恢复草稿与显示模型并调用原渲染函数重建动态内容，返回undefined。Reader保存独立副本，在控件恢复前调用适配器；不持有可变引用，不接受Promise、函数或DOM。适配器损坏、恢复失败或控件结构不匹配必须报错。不要在恢复时执行保存、发送请求或覆盖外部持久数据。

所有surface root继续进入snapshotSelectors；不能缩小范围、删除失败卡、让Reader替换innerHTML、重载页面或吞掉错误来通过返回校验。用真实卡片入口连续两轮“定位→返回”，包括初始关闭的详情、嵌套选择器和已修改未保存的草稿；核对文字、选中结果、动态列表及下一次打开行为。至少一次在**已经打开嵌套选择器并增加未确认选项后**定位另一张卡，再返回、确认选择、保存并重新打开；另一次返回后取消，证明DOM显示与实际保存模型一致。普通初始状态下的Runtime Audit不能代替这个场景。

正式validate-output前可用包内validator在工作区的临时输出位置预检当前草稿，并修正自身生成问题。预检不是成功Receipt，也不写旧Run；正式入口一旦restart_required，保留现场并使用新Run，不能修改冻结安装树。预检错误需定位到具体状态或组件，再继续，不能靠盲目改初始文案反复重试。

## 保留结构，不继承过时业务

- 当前 PRD／用户裁决确定目标规则，真实页面／现行代码确定现状结构，现役原型确定增量修改对象；三者职责不同。
- 旧模板、旧校验与当前需求冲突时，保留操作流程、更新对应规则。不能整份照搬旧稿，也不能以规则更新为由整体重排页面。
- 同一个业务对象的不同关系分别追溯。例如“所属范围”和“可服务范围”不因都引用一个区域就使用同一删除限制。新增约束与原有约束分开；未知的既有保护不能擅自删除。
- PRD 没有写清且真实基线也不能补足的产品选择，集中列出最小缺口；不让首次生成猜测未提供的页面字段。用户已确认的补充应同步至获授权的 PRD／裁决记录，再供生成与说明引用。
- 文档版本号变化不等于交互变化。用户确认无交互变化时沿用交互比较，只更新受影响的范围与说明；不要重画或重复验收未改变的页面。

## 集合操作：追溯事实，不造契约

出现增删、排序、选择、切换、批量导入或多记录合并／胜出结果时，只核对本次涉及的操作、状态和消费结果能否追溯当前 PRD 的规则／验收项或已确认裁决。

- 已有集合契约或旧 PRD 正文提供等价事实时直接使用，不强制迁移文档、补新状态字段或重新审查 PRD。
- 定向核对匹配对象、顺序／优先级、空白含义、失败是否保留原状态、部分成功及重试的结果。只应用来源已有的规则；无对应场景不强行补全。
- 整体目标有歧义时标明具体受影响行为；未确认规则不定稿。纯展示列表不自动升级为集合写入设计。
- 关键约束通过实际错误反馈与结果演示呈现，不把后台处理术语堆到业务页面。
- 导入、导出和结果重用同时继承实际文件格式与往返能力；下载按钮存在、内部数组测试通过，不证明用户文件可用。用目标格式的真实文件走完读取、处理、失败导出与修正重导，保留原始列和值。未实现时明确记为该操作未完成，不能把正式格式静默替换成 CSV、改扩展名的文本或专用演示格式后宣称可用。

## 区分适用范围与证据覆盖

沿用当前 v4 的 `scopeEvidence`，不重复添加协议字段。客户截图和登录环境说明取样来源，不自动缩小产品适用范围；一个样本通过也不证明所有客户、角色或权限已通过。

产品级交互未改变的版本修订，不自动产生新页面或新变化卡；开发说明需要同步时，只改实际受影响部分。原样本、旧 Run 与原验证记录保持原版本，不伪造跨版本通过。

## 最终对照

涉及工作簿的交互型 light 和 Standard 页面均要交付可打开的文件。在页面业务脚本前放入 `<!-- prototype-workbook-tools -->`，用 `node scripts/embed-workbook-tools.mjs source.html output.html` 将本地 SheetJS 浏览器版、许可和通用读写函数嵌入最终单文件。文件支持由项目决定。第三方分发来源为 [SheetJS 官方浏览器版本](https://docs.sheetjs.com/docs/getting-started/installation/standalone/)。

模板按钮调用 `PrototypeWorkbook.downloadTable(filename, [headers])`。选择文件后用 `await PrototypeWorkbook.readTable(file)` 读取首张表，以当前需求校验必要表头，再调用 `processTable(table, 原因列名, (原行值, 原表头) => 错误消息数组)`。逐行校验成功再写入本地状态，返回空数组表示该行成功。每次记录使用实际返回的 success、failed、failureTable，失败文件用同一 downloadTable 输出。可在本地模拟主数据和后端存储，页面结果从本次文件计算。

行处理先在副本中解析字段和查找关联对象，确认查找结果存在且满足当前规则后，再读取其属性并一次提交该行。未知关联返回该行的错误数组，后续独立行继续处理。不要用外层 catch 将程序异常伪装成成功或普通数据错误。自测加入“无效关联行在前、合法独立行在后”，同时核对失败行未留下部分修改。文件名、单元格和错误文本按纯文本渲染，不拼入 HTML。

生成者在最终页面上点击真实按钮验证事件绑定，监听页面脚本错误；函数可调用不能证明入口已接通。将待上传文件、处理中状态、最近批次结果及历史记录分开保存。清除选择或更换文件不清空已完成批次，处理中禁用重复提交；新的无失败结果不沿用上一批失败文件。Standard 中让临时阅读定位恢复这些业务状态，文件对象保留在页面模型中，以可序列化的标识参与状态适配，不能将 File 放入 JSON 快照或靠重载页面恢复。

在隔离浏览器针对最终 HTML 实际触发下载，用独立表格工具打开模板、填入混合数据、上传并核对数量。打开失败文件比对原输入列、值、顺序和原因，修正后重导，再检查无失败时的下载入口。接受浏览器下载事件并读取文件字节，保留各次输入输出作为证据。具备本地 Playwright 的自动化测试可用隔离上下文载入本次生成的自包含 HTML，禁用网络访问。静态语法、提示文字和固定示例数分别记录其实际覆盖。

业务结果与阅读交付分开检查：先对照实际业务交互，再在实际交付的累计阅读入口检查内容与定位。底层 HTML 正确、临时构建成功，都不能代替最终入口验证。只用已批准的输入做首次生成；旧正式原型留作事后对照时，不作为生成答案输入。

有限场景通过要明确覆盖范围。若还需要维护者临时绕行启动或手工补页面，应记录为未闭合，不宣称工作流已经能独立完成。
