# 一次初始化与日常使用

1. 在维护者正式发布后安装固定 Git 来源的 `prototype-workflow@qqx-prototype`。
2. 告诉 Agent：“初始化原型工作流”，提供内部可信 profile 位置、已有 SSH 用户名和个人密钥路径。profile 由维护者通过内部可信渠道提供，不随插件公开。
3. 只在返回 `ready` 后开始需求。环境缺失由本人补齐；插件不会改系统环境、生成密钥、申请账号或更新中心机主机信任。

## 对话示例

- 新需求：“按这份 PRD 开始新原型，输出到我指定的新需求目录。”
- 持续修改：“继续这个输出目录的需求，把已确认的调整同步到原型和累计阅读稿。”换对话、PRD 改名和新 Run 都不等于新需求。
- 交付：“产品内容已收敛，请准备独立 Review 材料。”作者自审不能代替独立审查；插件不自动创建或跨对话发送任务。

先集中补齐原流程所需材料与授权。正式 PRD 回写须有对应授权；已有布局、交互和历史记录受保护。收到 `restart_required` 时保留现场，不能升级工具来绕过旧 Run 的约束。

## 更新与锁定

新需求触发对固定 marketplace 的刷新，再验证批准索引、归档、依赖和激活回执。没有常驻后台、全局 Hook 或自动业务上传。

`reload_required` 表示新发行已经安装，但当前会话尚未加载新入口：按提示重载客户端或新建对话，再从新入口开始同一未绑定需求。不能仅重新读取版本号便声称重载成功。

`fallback` 明确显示使用的有效旧版本；必须读取返回绑定中的 START-HERE 和核心 Skill。续接已有需求只读取需求绑定，不刷新，不沿全局默认 Skill 链接切换。已有需求的显式版本迁移不在首版范围内。

需求绑定保存于用户输出目录 `.prototype-workflow/requirement.json`。公司配置在用户配置目录，运行组件在用户数据目录；业务材料不写插件缓存。首次成功配置不可被不同 profile 静默替换。服务或主机信任变更时先由维护者通过可信渠道确认。

## 排错

| 状态 | 含义与操作 |
| --- | --- |
| configuration_required | 配置或身份缺失，补齐显示的本机输入 |
| authorization_required | 核对已有用户名、密钥和 ssh-agent；确实未授权再找权限负责人 |
| host_identity_blocked | 可信主机或 profile 不一致，停止并由维护者核对 |
| service_unavailable | 服务或传输不可用，保留错误码后重试 |
| query_probe_blocked | 服务结果被拒绝；list 通过也不代表目标项目权限 |
| 完整性失败 | 保留旧安装、绑定和成果，交维护者定位；不手改摘要或删除历史 |

失败会返回脱敏本地记录位置，记录仅含实际版本、状态和稳定错误码；无法保存时如实显示 unavailable。反馈只填写本地空白表，不自动上传，不附业务 PRD、代码、截图、原始 SSH 输出或身份信息。

## 维护者本地命令

在实际插件根执行 `python3.12 -B -m plugin_runtime.cli`，只支持 `setup/new/resume/run/feedback`。薄 Skill 给出明确参数；全部原生命令通过 `run --workspace <需求目录> -- prototype ...` 调用绑定版本。`--home` 仅用于隔离本机验证，不能用作跳过身份检查。

候选验证使用已有 npm 内容缓存和 Chromium 缓存恢复，不宣称无缓存冷安装。尚未承诺 Windows/Linux、其他 Agent 客户端、真实同事 SSH 权限、桌面 onboarding 或最终 GitHub 来源可用。
